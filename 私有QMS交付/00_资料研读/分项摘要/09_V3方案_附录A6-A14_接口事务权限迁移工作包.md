## 1. 核心摘要

V3方案附录A的 A6–A14（p60–70）是内部 QMS 设计方案的工程契约后半部分，规定接口、与原生图纸工作台的集成、事务与锁、权限、迁移、工作包和验收，全部是待实施的规格。

- **接口（A6）**：新业务使用统一错误结构；正式变更只走限定字段的命令端点，必须带 request_key（8..128 字符）和 expected_version，并按 (origin_id, operation, request_key) 做幂等。核心命令共 20 条（CMD01–12、CMD15–22），CMD13/14 是未确认的外部执行候选。事实保存与采纳分开：例如量具历史校准无法核实时，测值照常保存，但标为 pending_review。未配置签审策略时返回 POLICY_NOT_CONFIGURED。
- **集成（A7）**：规定 QMS 与原生 Axis 工作台（图纸、气泡、方案、表图实测）及相邻 PPS 服务的桥接方式：CMD16 下发工作台上下文；轮次与原生报告一一绑定；样本和原生项分别映射到稳定的 sample_id 和 requirement_revision_id；保存、导入、完成、发布、导出、删除、离开 7 类原生动作全部改走 QMS 命令，新 QMS 控制器是唯一写入口。
- **事务与权限（A8–A9）**：一次事务内依次鉴权、查幂等、加锁、核版本、写审计/outbox；后台用同库任务表。superuser 不隐含质量批准权，人工签审只认显式的 policy_revision。
- **迁移与独立运行（A10–A11）**：旧 IQC/FQC 单标为 legacy_header_only，不补造数量；迁移分步进行、可对账，不 DROP 表；QMS 可以不接 ERP/MES 独立运行。
- **工作包与验收（A12–A14）**：10 个工作包（W01–W07、W09–W11），首条主链为 W01→W05；工程批次 S0–S5；所列测试都是拟建，本轮没有执行。非功能验收不编造容量承诺。12 张表、CMD13/14、W08/W12 等候选只在 out_of_scope_proposals 中保留溯源，不计数，也不作为依赖。

**示例的处理规则**（p63 A6.2¶1）

1. 在生产接口中，如果量具的历史校准无法核实，成功响应仍会保存该 event，并返回 `admissibility=pending_review, reason=GAUGE_HISTORY_UNVERIFIED`。
2. 对 measurement 类型，本轮 evaluate 返回 `technical_state=insufficient` 和缺证据清单；single_count 类型按其未完成状态表达。
3. 后续的技术评估可以追加采纳决定，并保留当时的判断轨迹。
4. 真实的不合格值保存为已采纳事实和 nonconforming 项目判定。
5. 只有 single_count 会按完整的计数证据另外输出 accepted/rejected 批判定；不因检验失败而拒绝保存。

| 场景 | 锁对象与顺序 | 校验内容 |
|---|---|---|

#### 2.3.2 A8.2 内部后台任务（p65）

- 需要异步生成报告或异步导入时，用同库的任务表/outbox 保留：任务 ID、对象版本、请求摘要、状态、租约和重试信息。
- worker 领取短租约后执行生成，并以幂等方式确认结果；进程恢复后不会重复生成业务签署事实。
- 是否需要启用独立 worker，按实际容量决定；不预先引入消息中间件。
- 【交叉参考 V3方案 p47 A1】后台 worker 可以作为同一代码包的独立进程运行，使用同一数据库事务与任务表，初期不需要 Redis 或消息中间件。

#### 2.3.3 A8.3 后台权限与文件（p66）

- 任务携带创建人及对象范围，执行时和下载时都重验当前权限。
- 附件和导出文件使用私有存储，通过鉴权下载或带明确撤销窗口的短期 URL 提供；不能凭可猜到的 ID 访问，也不能借 worker 绕过对象过滤。
- 当前没有外部执行回执、inbox、物流或门户任务。

### 2.5 A10 历史兼容与迁移方案（p67）

#### 2.5.1 A10.1 legacy_header_only

- 现有的 IQC/FQC 单据头没有实测快照、轮次或业务签审。
- 迁移时追加 `legacy_state=legacy_header_only`，并保持 `qualified_quantity/unqualified_quantity=NULL`；既有详情明确"尚未在本执行模型中检验"。
- 不得根据"有检验时间/检验人"推定检验已完成，也不得自动填写合格数量。
- 首次进入执行时创建新的 round，显式采用当前适用的依据，并记录实际开始时间和迁移来源。
- 用户提供旧纸面证据时，作为 `historical_evidence_import` 处理，保留原件、已知发生时间、录入时间、映射和审核。如果需要重新评价，则形成新的判定，不能冒充当年已经签署。

出处：p67 A10.1¶1–¶2。

#### 2.5.2 A10.2 标准与原生报告

**标准**（p67 A10.2¶1）

- 现有的标准根和项目不改 ID。
- 为每份已发布的标准生成一个"迁移内容修订"：内容 hash 固定，来源标为 migration，不伪造批准。由政策决定是否重新批准或受控采用，之后才能用于新的执行。
- 草稿标准可以继续编辑，但提交后走新的修订路径。
- 旧的 status 暂时作为兼容投影，不能让旧客户端单独修改 published 来绕过新规则。

**原生报告**（p67 A10.2¶2）

- 如果库中存在原生报告，先只读盘点实际数据，按版本或内容摘要分类；不假设复制模型表一定为空。
- QMS 绑定的新报告采用新的事实账；旧报告保留原有的只读内容，并可以受控导入。
- 对已知的 200 样本数组，按原始 ID 和位置建立映射；缺少实体身份的标为"未知"；不自动对齐不同项目的第 N 个样本。

### 6.2 对气泡识别服务的接口要求

【推断】以下是把 A7 抽象成「QMS ↔ 气泡识别服务」的契约要点，供后续需求分析参考。

1. 气泡识别服务对每个识别出的特性，要输出稳定的"源项标识 + 图纸修订 + 页码 + 定位 + 显示气泡号 + 原文/截图"。QMS 再把它映射为 requirement_revision_id。气泡号只用于显示。
2. 识别服务（或其 UI）写入 QMS 绑定对象时，只能调用 QMS 命令（观察、证据接收、评估、报告）。识别服务自身的"发布/批准/删除/完成"对 QMS 绑定对象必须禁用或改为调用 QMS 命令。
3. 识别服务的 UI 如果嵌入 QMS，要遵守同源 iframe 退出握手和 CSRF 规则，并且不能自行传入 workspace。
4. 识别服务的分页和序号只是显示序号，必须映射到 QMS 的 sample_id。V3 的原生组件有每项 200 条的上限，私有方案需要核实自有服务的上限。
5. 识别出的单位或数值有问题时，原文照样保存（intake），但不当作合格的规范值。这与 A6.3 的规范化导入规则一致。
