## 0 结论摘要

1. **资料构成**：云质官方材料 3 份（方案介绍、功能汇总、规划方案），通用科普 1 份，团队自有的 V3 设计 2 份（70 页方案、73 页目录），以及业务图 18 张。云质材料用于参照“中小制造企业通用 QMS 的模块、实施方法与使用体验”；V3 是本项目最直接的设计依据。
2. **云质QMS 是什么**：面向中小/成长型制造企业的通用标准产品，共 29 项功能。
   - 覆盖：检验、NCR/客诉/CAPA、评审、量具、质量成本、项目、文档、供应商协同等。
   - 特点：字段与流程可配置、Docker 多租户、可公有/私有/本地部署、有 Android APP、可对接 ERP、2–3 个月上线【YZ方案 p2–10；YZ汇总】。
   - 资料中没有图纸气泡或特性识别能力，图纸只是检验规则的参考资料【YZ规划 img_04】。
3. **V3 是什么**：
   - 主线：图纸气泡或手录形成标准版本 → 引用确定标准版本的检验方案 → 五类检验（IQC、生产首件、IPQC、FQC、OQC）→ 真实报告 → 真实数据 SPC → NCR、CAPA/8D 反馈修订；量具与 MSA 提供测量系统评价。
   - 形态：单一企业、FastAPI + PostgreSQL + React 模块化单体，并桥接现有 Axis 工作台。
   - 现状：本轮只是“方案与可评审原型”，未实施生产【V3方案 p2】。
4. **V3 的导航口径**：10 个导航分组、29 个稳定入口、53 个工作面（P01–P51、P58、P61）。共 61 个编号，其中 8 个是候选（P52–P57、P59、P60）。155 项原始能力只是溯源数，不是实施范围【V3方案 p1；V3目录 p1–3】。
5. **V3 的硬规则**【V3方案 §5–§8；V3目录 R01–R36】：
   - 标准与方案是两个对象；
   - measurement 只证明被检样本和项目，single_count 才判批；
   - 复检开新轮次，原失败保留；
   - NCR、Hold、CAPA 各自关闭，NCR 不自动整批冻结；
   - 普通合格不加放行审批，签审只按显式策略；
   - 判定在服务器端，用精确十进制，实测只有一份事实账。
6. **气泡识别在 QMS 中的位置**：它是 QMS 的“要求入口”。识别结果经人工校核后成为带稳定特性 ID 的标准版本，再流向方案、检验、报告、SPC 和 NCR【V3方案 p4、p13、p15、p64–65】。
   - 气泡号只是显示号；自动识别不等于已批准标准；同一方案修订只有一个批准权威。
   - Axis 管原生图纸、气泡、方案编辑与表图录入；QMS 管业务适用、签审、事实账与判定。
7. **行业 FAI 不在当前范围**：V3 只建设“生产首件”，行业 FAI（AS9102/IAQG 9102 类）是候选 P60【V3方案 p10、p46】。但同类气泡产品（InspectionXpert、HighQA）常以 FAI 报告为核心交付，是否纳入是高影响的待决事项。
8. **云质 29 项与气泡识别的关联**：
   - 强关联：检验规则（#24）、来料/首件/完工检验（#1、#2、#3）、数据录入方式（#26）；
   - 中等关联：出货检验（#4）；
   - 弱或无关联：网络销售、采购订单、质量成本、项目管理、登录、部署等。
9. **初步优先级【建议】（待确认）**：
   - P0：基础资料、IAM 与审计；图纸气泡 → 标准 → 方案 → 场景；IQC、生产首件、FQC 及共用的轮次/样本/事实账；手工与 Excel/CSV 录入；真实报告；NCR、处置、Hold；私有化部署。
   - P1：IPQC、OQC、SPC 与能力分析、量具与 MSA、CAPA/8D、客诉、供应商质量、版本对比与变更评估、模板与 SIP、看板与通知、全景追溯。
   - P2 或不做：审核、文控、培训、周期试验、质量成本、项目管理、网络销售、采购订单、门户、原生 APP。
10. **云质与 V3 的关键差异**：

    | 维度 | 云质 | V3 |
    |---|---|---|
    | 租户 | 多租户，按域隔离 | 单企业 |
    | 技术栈 | Node.js、MongoDB、Redis、RabbitMQ | FastAPI、PostgreSQL、同库 outbox |
    | 可配置性 | 字段与审批流高度可配置 | 严格对象模型 + 显式策略 |
    | 判定 | 自动 P/F，回写 ERP | 分层判定 |
    | 供应商协同 | 供应商门户 | 在原 NCR 上登记供方回复 |

    【建议】以 V3 为骨架，吸收云质的实施方法和移动、通知、看板、追溯等体验点。
11. **资料冲突**（详见 §8.1）：
    - 任务背景称“44 张云质截图提炼 155 项”，但 V3 全文未出现“云质”，且原图的 8D 命名与云质截图不一致；
    - 业务图 11 是 2026-11-14 的旧基线，含“独立批准”“产品再放行申请”，与 V3 冲突；
    - 云质两份资料对技术架构的口径不一；
    - 功能汇总中英两表的报表板口径不一；

12. **最高优先的待确认问题**：
    - 私有 QMS 的产品形态，以及“私有”的含义；
    - 识别服务（Axis/PPS）与 QMS 的边界和契约；
    - 首期范围，以及首件、FAI 是否纳入；
    - 判定、批接受与签审策略；
    - 是否基于现有 QMS 代码库增量建设。
13. **原型实现度落差**：V3 原型的 53 个工作面中，27 个是“只读资料”，11 个是“本地命令”，15 个“按动作区分”（据目录各工作面“当前原型”行统计）。生产实现工作量大，估算不能以原型的可见程度为准。
14. **下一阶段【建议】**：按“功能需求分析 → 开发流程确定 → 设计稿 → 需求文档”推进。

## 2 云质QMS 产品画像

### 2.1 定位

- **产品类型**：面向“中小型/成长型制造企业”的标准化 QMS 产品，与另外两种路线对比：
  - 低代码平台：云质认为其“无法实现业务逻辑、流程管理以及深入的多维度质量数据分析”；
  - 专业产品：虽然“自定义修改功能受限”，但上线快、成功率高【YZ方案 p2】。
- **覆盖范围**：全供应链、全产品生命周期，子模块可独立使用或联动，可与 ERP/MES/OA 集成【YZ方案 p2】。
- **目标**：检验“现场化、无纸化、实时化”，管理“在线化、流程化、透明化”【YZ方案 p3】。
- **建设目标分四个层面**：战略、运营、执行、系统，概括为“标准化、流程化、电子化、智能化”【YZ规划 img_01】。服务对象是质量作业层、控制层和决策层【YZ规划 §2】。
- **要解决的问题**：质量数据分散、数字化断层、供应链质量信息孤岛【YZ规划 §1；YZ方案 p1 图】。
- **与本项目的关键差别**：云质不涉及图纸气泡或特性识别。检验条目靠手工维护或批量导入【YZ规划 §3.2#5】；图纸、图片和检验作业指导书只是“检验规则标准”的输入资料【YZ规划 img_04】。

### 2.3 规划方案的关键业务机制（与本项目相关的部分）

**检验规则**【§3.2#5】
- 基础项：检验方法、项目、条目，缺陷项。
- 严重度评分：Mi/Ma/Cr 及扣分规则。
- 特殊特性：可对重要或关键特性做标记。APP 截图中可见 CTQ、CC 和“R”标记【img_29】。
- 检验类型：首检、巡检、末检、生产自检。
- 跳检规则：按批次、时间或数量。
- 抽样方式：AQL（GB2828.1-2012）、固定数、百分比。
- 物料检验标准：可设计数型或计量型，设公差和预警值，支持公式自动计算，“无需二次开发”。

**检验流程**【img_04；§4.3】
- 主链：ERP/WMS/MES/APS 触发报检 → 生成报检单 → 派工调度（跳批、合批、预警、升级）→ 手动录入或自动采集（检具、设备）→ 得出检验结果，进入统计分析或不合格品处理 → 合格/不合格结果及处理方式、数量回写 ERP。
- 报检单用四色标示状态：灰色未检，蓝色进行中，绿色合格，红色不合格【§4.3.2】。
- 巡检计划按设定间隔推送任务，例如每 2 小时一次【§4.3.3、img_05】。
- 预警值设在规格内、接近公差限的位置，用于提前预防【§4.3.5】。
- 检验批准走审批流，合格批次可设为免审批【§4.3.6、img_17】。
- 检验报告自动生成，可用内置模板或客户自定义模板，并可对外发送【§4.3.7、img_18】。

**不合格品处理**【§4.4、img_06】
- 流程：不合格品来源 → 登记 → 判断是否需要物料审核（MRB）→ 最终处理 → 审核并关闭。另有一条支线判断是否需要启动纠正预防。
- 处理过程中可登记质量成本和费用承担部门；来料不合格信息可直接公开给供应商。

**供应商协同**【§4.5、img_07–09、img_20】
- 供应商用 QMS 账号，在发货前录入出货检验（OQC）数据。
- 数据按“供应商 / 内部”两种来源区分，可与内部 IQC 对比合格率和箱线图。
- 供应商端有报检单、检验记录、不合格信息、CARs、周期性试验、评审管理和文档。

**CAPA/8D**【§4.9、img_23–25】
- CAR/SCAR 来源于不合格品、客诉和问题发现。
- 8D 阶段为：D1 建立团队、D2 定义及描述问题、D3 临时措施、D4 根本原因分析、D5 选择和验证纠正措施、D6 实施永久对策、D7 采取预防措施、D8 感谢团队成员。
- 8D 报告可自动生成并打印。

**评审管理**【§4.10、img_10、img_26–27、img_31】
- 评审清单可设置权重和必过项。
- 评审时可展示同一评审对象前 5 次的评审信息。
- APP 支持现场分层审核（LPA）。

### 2.11 通用科普文章的补充要点【科普】

**检验标准**
- 同一物料可按供应商、客户、工序、检验类型设置不同的验收标准，即“一个标准，分类呈现”。
- 同族物料的共性检验项可抽成“通用标准”，直接引用。

**检验执行**
- 检验员只需录入数据，抽样数量和判定由系统计算（“傻瓜式 QMS”）。
- 检验过程中可随时查看图纸、历史缺陷和作业指导书。

**数据权限**：各车间数据对检验员相互隔离，管理层可查看部分或全部。

**客诉处理**
- 采用“两段式”：先快反遏制，再寻因改进。
- 一条客诉可涉及 N 个物料，每个物料可涉及 N 个缺陷。

**纠正预防与追溯**
- CAPA 可关联历史上的同类 CAR。
- 可用任务模板一键分发 CAPA 任务。
- 全景追溯可一键查出相关的检验、不合格、客诉、整改等记录。

| 标准版本（qms_basis_revision + requirement） | 编制 → 适用核对 → 生效 → 采用 → 变更 → 停用 | 来源为气泡或手录；标准不隶属于场景；提交后内容不可变，带 content_hash |
| 方案修订（plan、revision、plan_scene） | 同上 | 引用一个标准版本及版内项目，选定适用场景，设定 measurement 或 single_count 执行安排；不另录公差 |
| 质量批次、检验任务（四类独立主单）、轮次、样本、观察事件 | 任务：创建 → 确定依据 → 分配准备 → 取样 → 采集 → 完整性检查 → 判定 → 按策略签审 → 完成 | 任务固定场景、标准、方案三层快照；本轮样本数 n 只属于轮次；复检是新轮次 |
| 报告修订与签审 | none / draft / frozen / review_required / approved / superseded / voided | 签名绑定内容摘要；不合格报告也可以被批准 |
| 质量事件、NCR、处置行 | 登记 → 范围确认 → 必要控制 → 处置 → 验证 → 关闭 / 重开 | MRB 是决策机制；复检进入检验新轮次 |
| 质量限制 Hold（范围 + 受限动作） | 建立 → 有效 → 复核 → 解除 | 必须明确范围和动作；解除一项只影响该项 |
| CAPA/8D 案件 | 启动 → 调查 → 措施 → 实施 → 观察验证 → 关闭 / 重开 | 8D 是 CAPA 的一种方法；通过 sourceNcrId 引用原 NCR |
| 客诉案件 | 登记 → 确认 → 响应 → 调查 → 处理 → 客户反馈 → 结案 / 重开 | 内部完成不等于客户认可 |
| 量具、校准、MSA 研究 | 建档 → 使用 / 借还 → 校准 → 异常 → 维修 / 恢复 → 报废 | 恢复使用只面向未来；MSA 结论与校准状态分开保存 |
| 审核、受控文件、培训 | 各自独立的生命周期 | 各自关闭，互不替代 |

**轮次的四个状态维度**【V3方案 p53–54 A3.2】，避免一个“完成”同时混合多种含义：

| 维度 | 取值 |
|---|---|
| execution_state | planned / active / submitted / closed / voided |
| technical_state | measurement：conforming / nonconforming / insufficient；single_count：accepted / rejected 等 |
| report_state | 见上表“报告修订”一行 |
| policy_outcome | pending / auto_accepted / manual_review_required / accepted / rejected |

产品、批次、检验三条生命周期不能排成每个对象必须走完的流水线。同一批次不必依次经过五类检验【V3方案 p9；业务图 02】。

### 3.5 关键业务规则

1. **标准与方案分离**【V3方案 p13 §5.1；R01–R02；A49–A51】
   - 气泡或手录形成标准版本；方案显式引用一个标准版本及其中的项目。
   - 新标准不自动更换方案引用；新方案不回写旧任务；停用只阻止新采用，在途任务按原快照继续。
   - 模板只是编制起点，复制后形成独立修订。
   - 同一方案修订只有一个批准权威：Axis 原生内容冻结与 QMS 业务生效不能重复审批。

2. **measurement 与 single_count**【V3方案 p17、p51；R03、R14；A01–A02】
   - **measurement**：输出每个项目“符合 / 不符合 / 证据不足”。报告完成后的 scope_conforming 只覆盖本轮实际样本和项目，usage=evidence_only，不构成整批接受，也不授权使用或发运。
   - **single_count**：n、Ac/Re、计数口径和提前拒收安排都在方案里维护，开检时继承，不能临时覆盖；只支持整数件制的批量。
   - 历史上的非件制计数结果标记为 legacy_scope_unverified，不追认为批接受。

3. **批判定**【V3方案 p3、p14 §5.3、p17】
   - 服务器执行带版本的抽样规则，区分未完成、继续抽样、接受、拒收。
   - 证据完整且不良数 d ≤ Ac 才可接受；d 达到 Re 才拒收；禁止提前做接受决定。
   - 抽样表须来自经审核的授权标准或企业批准的规则，不复制版权受限的完整表；不支持的方法明确拒绝（A44）。
   - 批接受后，已发现的不良件仍要单独处置。

4. **证据与数值**【V3方案 p16–17 §6.3；A3.1；R04–R08】
   - **数值权威**：判定以原值字符串和规范十进制字符串为准，用 Decimal 比较；NUMERIC(30,12) 只是查询投影。例如上限 10.02、实测 10.0200000000000001，必须判为超差。
   - **缺失表达**：NA、免检、未测、无效、缺失分别表达；缺失不能补零或补合格。
   - **样本建模**：实体样本和重复读数分开建模。
   - **导入规则**：
     - 真实超差必须入账；
     - 格式错误与真实超差分开处理；
     - 提交是原子的、幂等的。

5. **复检与更正**【V3方案 p17 §6.4；A4.1；R09】
   - 提交后的事实只能追加更正，保留原值、原因及新旧关联。
   - 复检建新轮次，记录 parent_round_id 和原因；可选原样本子集或新取样本，但不能改变策略类型。
   - 子集复检符合不推导整批接受；原失败永远保留。

6. **六类结果彼此独立**【V3方案 p18 §7.1；R13、R32】：测量事实、技术判定、报告签审、接受依据、用途资格、实际执行，互相不能推导。

7. **避免过度审批**【V3方案 p18–19 §7.2】
   - 普通逐项实测完成即可，不额外生成放行申请。
   - 需要人工签审的动作必须有显式策略；未配置时返回 POLICY_NOT_CONFIGURED，不默认批准。
   - 双人审批、专项资格、限额都必须有企业依据。

8. **报告与 CoC**【V3方案 p19 §7.3；R12】
   - 报告固定：任务与轮次、方案摘要、采纳证据、原失败与处置、签审、模板与生成器版本。
   - 模拟预览带显著标记，不能签发；缺值显示为缺失，不生成随机值。
   - CoC 只在合同要求时必备，不新设独立签发岗位。

9. **质量限制（Hold）**【V3方案 p19–20 §7.4；A5.2；R15；A20–A21】
   - 必须明确范围和受限动作（如 use、ship）；NCR 不自动冻结整批。
   - 是否受限，按“请求的动作 × 对象范围的交集”计算。
   - “同批存在相关风险”与“本对象本动作受限”分开显示。

10. **NCR 与 CAPA 双闭环**【V3方案 §8–§9.1 p21–24；业务图 08；R26】
    - **NCR**：管本次处置，处置行记录对象、数量、单位和凭据。
    - **CAPA 的触发**：不是每张 NCR 的必附单，按严重度、重复发生、客户要求、审核发现、过程失控和风险触发。
    - **8D 阶段**：D0 可选；D1–D8 采用 ASQ 命名，即 D6 实施并验证效果、D7 防再发及体系更新、D8 团队认可和结案。
    - **有效性验证**：
      - 措施实施与有效性验证分开记录；
      - 观察期未到或验证失败时不能关闭；
      - 结果回流到图纸、方案、SIP、培训和供应商要求的修订。

11. **客诉**【V3方案 p24–25 §9.2】
    - 客户陈述与内部已证实的事实分开标识。
    - 遏制、实物处置、CAPA、客户沟通、客户结案各自记录。
    - 客户没有回复不推定为认可。

12. **供应商质量**【V3方案 p25–27 §9.3】
    - 只做供方资料、真实 IQC 统计，以及在原 NCR 上登记供方回复与验证；不建第二套 SCAR，不做准入、综合评分或门户。
    - 统计口径：
      - 完成原检的批次按批去重；
      - 分母为零时不显示 0%；
      - 完整样本按 sampleUnit 分组；
      - 复检通过不抹掉原问题。

13. **计量与 MSA**【V3方案 p27–28 §9.4】
    - 校准记录保留调整前（As Found）和调整后（As Left）的结果。
    - 失准时触发影响评估；恢复使用不追认历史测量，也不自动解除 Hold。
    - MSA 首个方法是平衡交叉型 Gage R&R：两随机因素 ANOVA，保留交互项；最低结构 2 零件 × 2 操作者 × 2 次重复；不预设 10%/30% 判据。

14. **SPC 与过程能力**【V3方案 p28 §9.5；A34–A35】
    - 由用户明确选择产品、方案修订和特性，只用同单位、可追溯的本地实测数据。
    - 目前只有 I-MR 图：
      - σ = MR̄ / 1.128；
      - I 图控制限为均值 ± 3σ，MR 图上限为 3.267 × MR̄；
      - 信号只判点超限。
    - 规格限与控制限分开；高 Cpk 不能用来放行具体批次。

15. **主数据与变更**【V3方案 p7–8 §3.2、p13–14 §5.2】
    - 主数据：
      - 每个字段只有一个权威源；
      - 同步冲突进入待处理队列，不按“最后更新时间”覆盖；
      - 已被引用的对象禁止硬删除。
    - 变更评估：
      - 要反查受影响的方案、开放任务、在制品、库存和已出库范围，再逐范围决定是否采用；
      - 已签发的报告不追改，只能生成替代报告。

16. **指标口径**【V3方案 p41 §13.1；R27】
    - 批接受率、单件不良率、缺陷数与 Pareto、首次通过率、NCR 关闭率、交付质量、校准与培训完成率、质量成本，各有自己的分母和区分要求。
    - 报表须带统计区间、口径、规则版本，并能下钻到明细。

### 3.6 角色与权限【V3方案 §10 p31–36；V3目录 p3–4；A9 p66–67】

**授权原则**
- 复用现有账号、会话、接口权限和对象范围，由服务端校验动作、对象、当前版本和证据。
- superuser 和技术管理员不自动获得质量批准权（R25、A15）。
- 业务始终按单一企业使用，不设多工厂选择器（p31）。

**六个演示身份**：检验员、质量工程师、质量负责人、生产主管、仓库执行人、系统管理员。它们是待确认的示例配置，不是企业岗位制度。
- 质量工程师可连续完成维护场景、标准、方案并开检、录数；检验员可从已有方案开检、录数。正常路径不强迫换人。
- 报告复核名单（reviewerRoleIds）和 Hold 解除名单（releaseRoleIds）逐条配置。本地的独立复核只校验演示角色不同，不能宣称已识别“同一自然人的多个账号”。

**职责类别**（p32–33）：检验执行、质量/工程、供方/客户、计量/统计、审核/文控/培训、系统管理。

**关键动作的配置边界**（p33–34）：方案生效、实测与更正、报告签审、处置与限制、CAPA 或审核关闭、计量恢复、CoC、资料导出——每个动作都分两部分：
- 所有实现都必须保持的约束；
- 有企业依据时才启用的策略。

委托不是当前默认功能。

### 3.7 技术决策【V3方案 §12 p39；附录 A1–A13】

**总体架构**【A1 p47】
- 技术栈：FastAPI + SQLAlchemy async + PostgreSQL + React/TypeScript，组成模块化单体。
- 部署：Web BFF、质量业务 API、受限集成 API 在同一部署中提供。
- 后台任务：worker 使用同库的任务表和 outbox，初期不引入 Redis 或消息中间件。
- 文件：图纸和正式附件存放在私有对象存储，通过鉴权下载；导出字段走白名单。

**适用版本**：现有 QMS 检出 417e5d2a…，迁移要求 20261110_0021_finished_product。文中新增的表、API、工作包都只是设计，未实施（附录 A 开篇，p47）。

**模块划分**【A2 p47–48】
- 保留：iam、oidc、catalog、sampling、drawings/axis。
- 新增：quality_basis、quality_controls、evidence、jobs。
- 扩展：inspections。
- 量具、MSA、SPC、CAPA 由 metrology、统计、quality_system 承载。

**数据模型**
- 拟增核心表 38 张，核心命令 20 条（CMD01–12、CMD15–22）。CMD13/14 和 12 张表已移入 out_of_scope_proposals【A2.1 p49；A6 p61–62】。
- 四类独立检验主单保留不变；共用一张轮次表，用四个可空外键加 num_nonnulls=1 约束归属【A4.1 p54–55】。
- qms_observation_event 是唯一的权威实测账，原生 measurement_sets 只做投影【A4.3 p58】。
- 主键用 UUID，时间用 TIMESTAMPTZ，另设 occurred_at 记录发生时间【A3 p52–53】。
- 草稿带 row_version；提交后只追加，更正用 supersedes_id 连接；触发器限制 UPDATE 和 DELETE【A3 p52–53】。

**命令协议**【A6 p60–63】
- 状态变更只走领域命令，不提供任意 PATCH 判定或批准状态的接口。
- 每个命令带 request_key 和 expected_version；幂等作用域为 (origin_id, operation, request_key)。
- 统一错误结构 {error:{code,message,details,retryable},request_id}；401、403、404、409、422、429、503 各有固定语义。
- FACT_SAVED_NOT_ADOPTED 是成功响应里的业务评估，不是 HTTP 失败。

**Axis 桥接**【A7 p64–65】
- 通过 workbench-context 接口下发上下文；用 qms_native_report_binding 绑定原生报告。
- 原生动作改造清单覆盖：保存、导入、完成/重开/复制、方案发布、报告导出、删除、离开握手。
- 原生的非 QMS 历史对象默认只读。

**事务**【A8】：鉴权 → 幂等检查 → 加锁 → 重读 → 版本校验 → 写入业务记录、审计和 outbox → 一次提交。

**迁移**【A10】
- 步骤：扩展表与可空列 → 回填可证明的内容 → 建索引和外键 → 双版本只读兼容 → 切换新写入口 → 最后收紧约束。
- 一旦产生新事实，不 DROP 表，也不用旧备份覆盖。

**非功能**【§13.2 p42；A13 p70】
- 性能按真实业务量做预算，覆盖 201 个样本的全检、千级特性的图纸等场景，并记录 p95。
- 做备份恢复演练。
- 时间按 UTC 存储。

## 5 图纸气泡识别在 QMS 中的定位

### 5.1 端到端数据流

```
[P45 零件] ──► ① 图纸导入（P02：图纸文件修订、来源 hash、零件关联）
                 │  Axis 持有图纸内容、版次、标注资产
                 ▼
             ② 气泡识别（识别服务产出候选特性 + 图面定位/截图片段）
                 │  “自动识别不等于已批准标准” [V3方案 p4]
                 ▼
             ③ 人工校核（P03：单位、公差、GD&T、关键度、不可让步标识）
                 ▼
             ④ 特性清单（特性稳定 ID；气泡号只是显示号；记录图纸修订、页码、原文）
                 ▼
             ⑤ 标准版本（P06：气泡来源与手录来源进入同一标准主账；内容不可变，带 hash）
                 ▼
             ⑥ 检验方案修订（P08：选标准版本 + 项目 + 场景 P61；measurement 或 single_count；报告策略）
                 │                    └─► SIP 检验指导书（P10）
                 ▼
             ⑦ 检验执行（P11–P16：任务固定场景/标准/方案快照 → 轮次 → 样本 → 观察事件）
                 │  录入方式：Axis 表图联动；或 P18 文件/设备导入（按气泡特性匹配）
                 ▼
             ⑧ 判定与报告（服务器判定 → P20 报告修订与证据清单 → 按策略在 P21 签审；CoC 按合同）
                 │  行业 FAI 报告：不在当前范围（候选 P60）
                 ├─► ⑨ SPC 与能力分析（P37/P50：按产品 + 方案修订 + characteristicId 选点）
                 └─► ⑩ NCR / Hold / 处置 / 复检（P23/P24/P58）──► CAPA/8D（P25）
                                                                     │
             ⑪ 反馈修订 ◄────────────────────────────────────────────┘
                （新标准修订 → 新方案修订显式采用；换图走 P04/P05 特性映射与逐范围采用；旧任务和报告不回写）
```

各环节的依据与要点：

1. **图纸导入**【P02；F007、F010】
   - 功能：上传与检索图纸，管理版本，关联零件。
   - 来源字段：drawing、package、history、source_item、hash【V3方案 p57】。
   - 图纸的采用由 QMS 业务对象和图纸使用授权管理【A1 p47】。
   - 资料没有说明支持哪些图纸格式；F037 中“3D”只出现了页签。

2. **气泡识别**
   - 资料没有定义识别算法。V3 只借鉴了 InspectionXpert 的做法：框选尺寸后，同时生成气泡、原图截取和特性字段，识别结果仍需核对【V3方案 p4、S11】。
   - 识别引擎归属 Axis 还是 PPS，资料未说明，见 KQ2。

3. **人工校核**【P03】
   - 在可编辑的修订中维护特性、单位、公差、关键度和不可让步标识。
   - 已批准的版本只读；任何修改都形成新修订【V3目录 P03】。
   - 原图字段（F009）：编号、名称、尺寸标注、公称值、上下偏差、检验要求、类型（尺寸、几何、螺纹、粗糙度）、关键度。

4. **特性清单**
   - 每条要求保留：图纸修订、页码、气泡显示号、原文或截图片段、特性身份、单位、公差或属性表达、检验方法。
   - 气泡移动或重新编号，不改变特性身份【V3方案 p13】。
   - 注意：“方法”字段的编辑目前尚未接通【V3方案 p13、p57】。

5. **标准版本**【P06】
   - 气泡来源和手录来源进入同一个标准主账。
   - 采用记录保存源图纸、方案及修订 ID 和特性映射，不凭名称合并【A2.2 p50】。

6. **检验方案**【P08】
   - 选定标准版本、版内项目、适用场景和执行安排，不另录公差。
   - Axis 原生方案蓝图只负责呈现；业务适用关系由 QMS 管理【A4.2 p56】。

7. **检验执行**
   - 建任务时，在同一事务中核验引用关系，并固定场景、标准、方案三层快照。
   - 两种录入方式：
     - Axis 表图联动：原生项映射到 requirement_revision_id，工作台上第 N 个样本映射到 sample_id【A7.1 p64】；
     - 文件导入：把测量文件中的特性匹配到图纸或方案特性；列映射和特性匹配是两个层级【F059–F060】。

8. **报告**
   - 报告详情可在图纸气泡与特性之间切换【F066】。
   - CoC 和资料包只在适用时提供【F052–F053；§7.3】。
   - **FAI 不在当前范围**，三处资料一致：
     - V3 只建设生产首件，“不新增行业FAI 入口、流程或鉴定表单”【V3方案 p10】；
     - HighQA 的 FAI“不当作本项目新增需求”【V3方案 p4】；
     - 业务图 03 写明行业 FAI“仅解释术语，专用模块尚未确认”。

9. **SPC**：按 characteristicId 选取数据点，不混用不同图版、方案快照或单位【V3方案 p28】。

10. **NCR/CAPA**
    - NCR 记录对应的气泡或项目、实测值与公差【F075】。
    - CAPA 的结果回流到图纸、方案、SIP 的修订【V3方案 p24】。

11. **反馈修订**【V3方案 p13–14；业务图 04；A10、A51】
    1. 新图纸修订先做特性映射，结果分为沿用、增删、拆并，或“无法确认”（转人工评估）。
    2. 生成影响清单。
    3. 逐个范围决定是否采用新版本。

## 7 关键差异与取舍

| 维度 | 云质 | V3 | 利弊 | 【建议】 |
|---|---|---|---|---|
| 租户与组织 | Docker 多租户，按域隔离，支持多工厂 | 单企业，无租户层，无多工厂选择器 | 多租户便于 SaaS 运营，但复杂度高、隔离风险大；单企业简单可靠 | 保持单企业数据模型，每个客户部署一个私有实例；域隔离待确认 |
| 技术栈 | Node.js v12、MongoDB v4、Redis、RabbitMQ、Docker | FastAPI、PostgreSQL、React，同库 outbox，不用 MQ | 文档库灵活，但事务和精确数值支持弱；PostgreSQL 的事务、约束和 Decimal 更适合做证据账 | 沿用 V3 和现有代码 |
| 可配置性 | 字段改名或新增、参数、审批流、检验类型都可配；报表最多 80 个图表 | 严格对象模型，固定 5 个场景，不做 BPM 和动态菜单 | 可配置利于快速适配客户，但会削弱判定和审计的一致性 | 核心对象保持严格；只开放显示名、多语言、报告模板、签审策略、不参与判定的扩展属性等有限配置 |
| 判定与放行 | 自动判 P/F；检验批准可免审；结果回写 ERP | 分层判定；measurement 不判批；不加放行环节 | 自动 P/F 用户熟悉，但容易把“逐项符合”误当成“批接受” | 采用 V3 规则，同时支持在方案中显式配置接受策略；ERP 只回写接受依据 |

| 移动端 | Android APP、PDA、扫码、拍照 | 无；首版不承诺离线 | 现场效率高，但开发成本也高 | P1 做适配平板的 Web；原生 APP 待定 |
| 通知与升级 | 邮件、企业微信、系统通知；任务升级、自动重新分配 | 只有工作台待办；对外发送待确认 | — | P1 做站内通知和邮件；企业微信、钉钉放 P2 |

| 图纸与特性 | 无；检验规则手工维护 | 核心能力：气泡 → 标准 → 方案 | 本项目的差异化所在 | P0 |

## 8 风险、矛盾与待确认问题

### 8.1 资料之间的冲突

1. **44 张原图的来源无法证实是云质。**
   - 任务背景称“由 44 张云质截图提炼 155 项能力”，但两份 V3 文档全文没有出现“云质”二字，只写“原型功能清单 / 原始截图 / 原图 IMG01–IMG44”【V3方案 p3】。
   - 原图中的能力（气泡标注、3D、CMM 导入、SCAR、准入评分）在云质资料里都没有出现。
   - 原图的 8D 阶段是“D7 验证 / D8 标准化”【V3方案 p24；F082】，云质截图则是“D7 采取预防措施 / D8 感谢团队成员”【YZ规划 img_24】。
   - V3 目录 Q01 也说明，原图来自“不同原型、不同产品名”。
   - 结论：不能把 155 项当作云质的功能；原图来源待确认。

2. **业务图 11 是旧基线，与 V3 冲突。**
   - 该图图题为“12 量具恢复与历史失准影响”，页眉为“QMS 业务架构与流程图册｜业务设计基线｜2026-11-14”。
   - 图中有“独立计量批准人”“独立批准恢复使用”“风险负责人批准”“产品再放行仍单独申请”。
   - V3 规定独立性只按显式策略启用，普通合格不加放行申请【V3方案 p18–19、p27–28】，两者冲突，以 V3 正文为准。
   - 业务图 13b 中“审核人员满足独立性？”这一步，也应理解为“按适用制度”的条件分支。

3. **业务图的文件名与图题不一致，引用时以图题为准。**

   | 文件 | 文件名 | 图题或图内编号 |
   |---|---|---|
   | 02 | 产品与批次生命周期 | 场景 标准 方案与检验生命周期 |

   - 方案 PDF：Docker 多租户 + Redis/RabbitMQ + MongoDB 主从。
   - 规划方案：“微服务 + 大数据架构”，但技术要求只是 Node.js + MongoDB、2 台 16G 服务器【YZ方案 p3、p5；YZ规划 §4.1.1、§6.1】。

5. **云质的部署取向与本项目不同。**
   - 方案 PDF 推荐公有云，并称其“安全性更高”【YZ方案 p4】。
   - 规划方案的技术要求却是容器化本地部署【YZ规划 §6.1】。
   - 本项目要求私有化。

6. **云质的导入顺序前后不一。**正文与导入步骤图对出货、不合格品的先后顺序不同【YZ方案 p5 与 p10 图】。

7. **云质功能汇总的中英两表口径不一。**【YZ汇总 #4、#14、#22】
   - 报表板：中文写“每个客户最多 80 个报表”，英文写“每个用户 80 张图、大屏 5 分钟刷新”。
   - OQC：英文多出“自动生成 COC”。
   - 文档管理：英文多出“锁定 / 解锁”。

8. **多工厂与单企业的矛盾。**云质支持多工厂、按域隔离【YZ方案 p3；YZ规划 §4.1.4】；V3 是单一企业、不设多工厂选择器、无租户层【V3方案 p31、p47】。

9. **判定方式不同。**云质自动判 P/F 并回写 ERP【YZ汇总 #1–4；YZ方案 p9 图】；V3 中 measurement 不形成批接受，usage=evidence_only【V3方案 p17、p51】。

10. **审批方式不同。**云质有审批流引擎【YZ规划 §3.2#3、§4.3.6】；V3 不做 BPM，未配置不批准，不默认增加审批【V3方案 p18–19、p55】。

11. **V3 内部的候选口径不一。**
    - 封面说“8 项候选”，对应 P 编号。
    - §17 的候选表有 10 行，多了其他 MSA 方法、物流、额度、资格平台等非页面项。
    - 两者粒度不同，需求分析时需要合并成一张候选清单。

12. **原图能力的映射与 V3 规则存在张力。**F022 方案签审、F038 首件审批放行、F054 出货放行审批等原图能力，仍映射在工作面上；但 V3 规则是“普通合格不加放行、签审只按显式策略”。原图出现过的能力不等于必须建设。

    - 实测 50.12 超过上限 50.10，却被标为规格内；

    - 逾期天数算错；

14. **MSA 的来源需要标注清楚。**F128 显示原图只有 MSA 入口；P51 是按用户 2026-11-15 的明确要求新增的。这属于范围变更而不是矛盾，但追溯时应注明来源是“用户明确要求”。

### 8.3 主要风险

- **范围膨胀**：155 项原图能力加上云质的 29 项，很容易被误读为需求。需求分析阶段必须用“已确认范围 + 候选清单”来管理范围。
- **实现落差**：53 个工作面中有 27 个在原型里只是只读资料。生产实现需要从数据模型、命令到界面全链路建设【V3方案 p2、p43】。
- **规则复杂**：六类结果、四个状态维度，用户理解成本高。设计稿需要把这些复杂度收敛在对象页内部。
- **企业策略缺失**：签审、接受规则、抽样授权等都还没确定，相关功能只能先做到“待配置”状态。
- **原生组件约束**：原生组件有 200 个样本的上限，且数据是数组形态，需要靠适配器解决，存在双写风险【A4.3】。
- **性能未经验证**：千级特性的图纸、超过 200 件的全检尚未压测【§13.2】。
- **流程串行**：团队流程是后端先行、前端在后，接口文档的质量直接决定联调效率。
- **资料冲突**：§8.1 列出的冲突如果不清理，会导致需求依据不一致。

### 9.2 组织方式与顺序

1. **先开需求决策会**，关闭 KQ1–KQ7，输出范围基线，然后再展开 P0 的需求分析。

   - 需求分析由产品牵头；
